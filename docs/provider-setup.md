# Production provider setup

Configure these as private Vercel environment variables. Do not post secret values in GitHub, support reports or chat. A successful website deployment does not provision these provider accounts or apply database migrations.

| Service | What the operator must supply |
| --- | --- |
| App sessions | `NEXTAUTH_URL=https://delaware-ftc-hq.vercel.app` and a generated random `NEXTAUTH_SECRET` with at least 32 bytes of entropy |
| Google | `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` from a Google OAuth app; registered callback `https://delaware-ftc-hq.vercel.app/api/auth/callback/google` |
| Microsoft | `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, and reviewed `MICROSOFT_TENANT_ID` (`common` supports configured personal and work/school account types); callback `/api/auth/callback/azure-ad` on the canonical domain |
| Apple | Apple Developer account, a Sign in with Apple Services ID (`APPLE_CLIENT_ID`), and a signed client-secret JWT (`APPLE_CLIENT_SECRET`) generated using the developer Team ID, Key ID and private key; callback `/api/auth/callback/apple` on the canonical domain. Record the client-secret expiry and rotate it before expiry. Review Apple email-relay domain requirements if using Hide My Email. |
| Email links | Resend account, a verified sending domain with required DNS records, a send-authorized `RESEND_API_KEY`, and `EMAIL_FROM` using that verified domain. Configure the sender domain without open/click tracking for authentication links. Test delivery and link scanners on the actual supported email clients. Ordinary `@icloud.com` addresses use this email-link option; Apple ID is a separate sign-in method. |
| Database | `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_D1_DATABASE_ID`, and a restricted `CLOUDFLARE_D1_API_TOKEN` with D1 Read and Write permissions |
| Private files | `CLOUDFLARE_R2_BUCKET_NAME`, `CLOUDFLARE_R2_ACCESS_KEY_ID`, `CLOUDFLARE_R2_SECRET_ACCESS_KEY`, with bucket-scoped object Read and Write permissions. Keep the bucket private. |
| Scheduled cleanup | Random `CRON_SECRET`; Vercel calls `/api/maintenance/retention` once daily at 07:00 UTC. Check its execution history. A request with no valid secret returns 401. Activity-based cleanup remains a second path. |
| Release controls | The current approved `MYFTC_READINESS_RECORD`, `MYFTC_DATA_ENABLED` (keep false until approved), `MYFTC_SELF_SERVICE_ENABLED` (keep false unless self-service is separately approved), and emergency `MYFTC_SERVICE_PAUSED` |

At least one configured sign-in method and the session secret are required. Email also requires D1 and the authentication tables. The sign-in page lists only methods with the necessary configuration. Google, Microsoft, Apple and email identities are separate; identical emails do not automatically transfer team roles between methods. Email session IDs use an internal random user ID, not the email address. In roster-based releases, accounts and teams must be approved on the release roster before access is granted.

Self-service is a separate, closed-by-default access model. It requires a reviewed `public-multi-team` readiness record for the exact build with `accessModel: "self-service"` and a `selfServiceReview` containing real `evidence`, `reviewer` and `reviewedAt` values. The existing readiness checks and checklist still apply. The operator must explicitly enable both `MYFTC_DATA_ENABLED` and `MYFTC_SELF_SERVICE_ENABLED` only after the actual services and review are ready. Adult team creators and recipients of adult-role invitations must confirm that they are at least 18; this is self-attestation, not age or identity verification. A team's admin must confirm the appropriate safeguards and permissions outside this checkbox.

In the student-founder flow, a student declares that they are 13–18 and have the required parent or guardian permission; this declaration does not independently verify age or permission. Invited student members make the same declaration. The founder can invite students and use the shared workspace without an adult joining. A founder can remove other student members while no adult administrator is present and can delete the team while they remain its sole member. A mentor joining does not remove that ability; the founder cannot remove adult roles. The founder can continue issuing invitations while their founder permission remains active; an admin can revoke it by changing their role or removing them. Adult-only actions remain reserved for adult roles.

## Database migration

Before enabling messaging or email, the database administrator must back up the intended database and apply `drizzle/0002_messaging_and_email.sql` through the organization's approved Cloudflare D1 migration workflow. It adds chat messages, messaging settings, DM blocks, authentication lookups, hashed verification tokens and mail-rate counters. Use the exact database intended for the production environment. These migrations are not automatically applied by a Vercel build.

Confirm `0000_tidy_infant_terrible.sql` and `0001_privacy_controls.sql` were previously applied. Apply `0003_student_founder.sql` after the earlier migrations before enabling student-created teams; it adds a server-controlled founder flag to memberships. Apply `0004_native_auth_handoff.sql` after the earlier migrations before using Google sign-in in the iPhone app; it adds short-lived, single-use handoff records. For a new empty database, apply migrations in order. Do not rerun table-creation migrations against an existing database without checking its migration history.

## Required verification after setup

Use separate fictional test accounts to verify each enabled provider, callback, sign-out, account changes and invitation flow. In roster-based mode verify that an unapproved adult cannot become an operator. In self-service mode verify that adult confirmation is required for creation and adult invitations, that student roles cannot bypass it, and that teams cannot see each other's records. Verify that multiple adult operators can manage a team. Test group messages, participant-only DMs, disabled-DM behavior, blocks, explicit reports, removal, retention cleanup and team erasure against the actual D1 database. Check private R2 downloads and cleanup. Keep the real-data gate closed until the adult/school review and hosted checks are accepted.

For the iPhone app, apply the native handoff migration and test Google sign-in on an actual device or simulator with the production-equivalent HTTPS host. Confirm that the system sign-in window returns to the same account in the app, cancellation leaves the app usable, account changes do not overwrite a newer session, expired and reused handoffs fail, and sign-out works. The native handoff currently supports Google; Apple and Microsoft sign-in remain available on the website when configured. Review the current App Store sign-in requirements and the app's applicable exceptions before submission.
